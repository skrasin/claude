# Анализ рисков и рекомендации по безопасности сайта-витрины fstravel.com

**Объект:** публичный сайт-витрина https://fstravel.com/ (туроператор FUN&SUN / ФС Тревел)
**Тип работ:** пассивный анализ модели угроз + рекомендации (без активного сканирования и эксплуатации)
**Дата:** 2026-08-23
**Фокус запроса:** как публичный сайт может быть использован как вектор атаки на внутренние системы, платёжные шлюзы и клиентские данные.

---

## 0. Важное ограничение по объёму работ

Живое сканирование сайта в рамках этой сессии **выполнить не удалось**: исходящий сетевой доступ
к `fstravel.com` заблокирован egress-политикой рабочего окружения (проксирование вернуло 403 на CONNECT).
Обход этого ограничения не выполнялся — это запрещено политикой.

Поэтому документ ниже — это:
1. **Модель угроз** для сайта-витрины туроператора (какие векторы реально применимы).
2. **Приоритизированные рекомендации**, что проверить и что исправить.
3. **Готовый чек-лист пассивных проверок** (раздел 9), которые нужно прогнать по «живому» сайту —
   вручную или из окружения с сетевым доступом. Эти проверки неинвазивны и безопасны для продакшена.

Ни одна рекомендация не заменяет полноценный пентест и аудит по согласованию с владельцем системы.

## 1. Ключевой тезис: «витрина» почти никогда не бывает статичной

Формально сайт — витрина с информацией, но на практике у туроператора на том же домене
(или на поддоменах) обычно живут:

- **поиск и подбор туров** (запросы к backend/GDS/движку бронирования);
- **онлайн-бронирование и оплата** (интеграция с платёжным шлюзом/эквайрингом, банком);
- **личный кабинет клиента** (ПДн, история заказов, документы);
- **кабинет турагентов / B2B-портал** (670+ агентств → массовый доступ, привлекательная цель);
- **формы обратной связи, подписки, обратного звонка** (ввод пользователя → backend/CRM);
- **интеграции**: CRM, ERP, почтовые рассылки, аналитика, чат-виджеты, карты.

Именно эти динамические функции, а не статический контент, и есть поверхность атаки на внутренние
системы, платежи и данные клиентов. Первый шаг аудита — **инвентаризация всей поверхности**
(домены, поддомены, эндпоинты, формы, API, интеграции), потому что защищать можно только то,
что учтено.

## 2. Как витрина превращается в вектор к внутренним системам (модель угроз)

| Вектор | Механизм | К чему ведёт |
|---|---|---|
| Инъекции через формы/поиск/параметры | SQLi / NoSQLi / command / SSTI | Доступ к БД, CRM, выполнение кода на backend |
| SSRF через серверные интеграции | Сервер бронирования ходит по URL, управляемому извне | Доступ к внутренней сети, метаданным облака, служебным API |
| Некорректная авторизация (IDOR/BOLA) | Перебор ID заказа/клиента | Чужие брони, ПДн, документы |
| Компрометация сторонних скриптов (Magecart) | Внедрённый JS крадёт данные карт с формы оплаты | Утечка платёжных данных, штрафы PCI |
| Захват поддомена / забытые dev/stage-стенды | Dangling DNS, открытые тестовые окружения | Фишинг под доверенным доменом, утечка исходников/секретов |
| Раскрытие секретов (.git, .env, source maps, ключи в JS) | Файлы/артефакты на проде | Ключи API, доступ к внутренним сервисам |
| Слабая аутентификация B2B/админки | Брутфорс, отсутствие MFA, дефолтные креды | Захват кабинета агента/администратора → массовый доступ к данным |
| Открытая/недокументированная API-поверхность | Скрытые эндпоинты, GraphQL introspection, mass assignment | Обход UI-ограничений, эскалация |

Главный архитектурный принцип защиты: **публичный сайт не должен иметь прямого доступа
к внутренним системам и БД**. Между ними — сегментация сети (DMZ), API-gateway с авторизацией,
отдельные сервисные учётные записи с минимальными правами, отсутствие прямых подключений
веб-фронта к продакшн-БД.

## 3. Приоритет P0 — критично (устранить в первую очередь)

### 3.1. Платёжные данные и защита от веб-скиммеров (Magecart)
- **Не хранить и не обрабатывать данные карт на своей стороне.** Использовать hosted payment
  page / редирект на страницу банка-эквайера или платёжную форму в изолированном iframe (PCI SAQ A).
- **Обязательный 3-D Secure (2.0)** на всех платёжных операциях.
- На страницах, связанных с оплатой, — **строгий CSP** и **минимум сторонних скриптов**
  (в идеале — ноль: никакой аналитики, чатов, тегов на checkout-страницах).
- **Subresource Integrity (SRI)** для всех внешних `<script>`/`<link>`.
- Регулярный контроль целостности JS на платёжных/чекаут-страницах (мониторинг изменений).
- Соответствие **PCI DSS**; подтвердить, какой уровень SAQ применим, и что он реально соблюдается.

### 3.2. Разделение витрины и внутренних систем
- Сетевая сегментация: веб-фронт в DMZ, нет прямого сетевого пути к продакшн-БД/CRM/ERP.
- Все обращения к внутренним данным — только через API-gateway с аутентификацией и авторизацией.
- Сервисные учётки с принципом наименьших привилегий; секреты — в secret manager, не в коде/конфиге на диске.

### 3.3. Инъекции и валидация ввода (везде, где есть ввод: поиск, формы, параметры, API)
- Только параметризованные запросы / ORM; запрет конкатенации ввода в SQL/NoSQL/команды/шаблоны.
- Валидация по «белым спискам», контекстное экранирование вывода (против XSS).
- WAF в режиме блокировки перед приложением как компенсирующий контроль (не замена исправлениям).

### 3.4. Авторизация и IDOR/BOLA (личный кабинет, брони, документы, B2B)
- Проверка прав доступа на сервере для **каждого** объекта (заказ, клиент, документ), а не по UI.
- Непредсказуемые идентификаторы (UUID) вместо последовательных числовых ID.
- Тест: сможет ли пользователь A открыть заказ/данные пользователя B, поменяв ID в запросе.

### 3.5. Раскрытие секретов и артефактов на проде
- Проверить и закрыть: `/.git/`, `/.env`, `.bak/.old/.zip` бэкапы, `/debug`, `/phpinfo`,
  server-status, открытые source maps (`*.map`), swagger/openapi без авторизации.
- Убрать из клиентского JS секретные ключи API (в браузер попадают только публичные ключи с ограничениями).

## 4. Приоритет P1 — высокий

### 4.1. Аутентификация и сессии
- **MFA обязателен** для админов, сотрудников и кабинетов турагентов (B2B — приоритетная цель).
- Cookies: `Secure`, `HttpOnly`, `SameSite`; защита от session fixation, ротация сессии при логине.
- Rate limiting и защита от брутфорса/credential stuffing на логине и восстановлении пароля.
- Единообразные ответы, не раскрывающие существование аккаунта (против user enumeration).
- Безопасное восстановление пароля (одноразовые токены с TTL, без утечки в реферере/логах).

### 4.2. Защита клиентских данных (ПДн, 152-ФЗ)
- Минимизация: не собирать/не отдавать больше данных, чем нужно; маскирование в интерфейсах.
- Шифрование ПДн в покое и в транзите; ограничение экспорта/выгрузок.
- Разграничение доступа сотрудников к данным клиентов + журналирование доступа.
- Соответствие 152-ФЗ (согласия, локализация ПДн граждан РФ, политика конфиденциальности).

### 4.3. API-безопасность (OWASP API Top 10)
- Инвентаризация всех эндпоинтов, закрытие «теневых»/устаревших версий API.
- Авторизация на уровне объектов и функций; защита от mass assignment.
- Отключить GraphQL introspection в проде (если используется GraphQL).
- Rate limiting и квоты на API.

### 4.4. Транспорт и HTTP-заголовки безопасности
- TLS: только TLS 1.2/1.3, современные шифры, корректная цепочка сертификатов, без устаревших протоколов.
- `Strict-Transport-Security` (HSTS, с preload после проверки), редирект HTTP→HTTPS.
- `Content-Security-Policy` (в идеале nonce/strict-dynamic), `X-Content-Type-Options: nosniff`,
  `X-Frame-Options`/`frame-ancestors` (антикликджекинг), `Referrer-Policy`, `Permissions-Policy`.
- Убрать раскрытие версий в заголовках (`Server`, `X-Powered-By`).

### 4.5. Поддомены, DNS и забытые окружения
- Инвентаризация всех поддоменов; поиск dangling-записей (риск subdomain takeover).
- Закрыть/убрать публично доступные dev/staging/test-стенды — частый источник утечек и «мягкая» точка входа.
- Убедиться, что нерабочие/старые интеграции и записи удалены.

### 4.6. Защита бренда и клиентов от фишинга (email)
- Настроить и проверить **SPF, DKIM, DMARC** (DMARC в режиме quarantine/reject) для доменов рассылок.
- Это снижает риск рассылок-подделок под брендом FUN&SUN, ведущих к краже данных клиентов.

## 5. Приоритет P2 — важно

- **Supply chain / сторонние скрипты:** аудит всех тегов, аналитики, чат-виджетов, менеджеров тегов;
  минимизация, SRI, регулярный пересмотр. Каждый внешний скрипт — потенциальный канал компрометации.
- **Загрузка файлов** (если есть: сканы паспортов, документы): валидация типа/размера, антивирус,
  хранение вне webroot/в отдельном бакете, без выполнения.
- **SSRF-защита** для всех серверных интеграций (бронирование, GDS, курсы валют): белые списки хостов,
  запрет доступа к внутренним адресам и облачным метаданным.
- **Rate limiting и антибот** на формах, поиске туров, API — против скрейпинга цен, спама, DoS-нагрузки.
- **Логирование и мониторинг:** централизованные логи безопасности, алерты на аномалии,
  мониторинг целостности файлов на проде, план реагирования на инциденты.
- **Патч-менеджмент:** актуальные версии CMS/фреймворков/библиотек; процесс отслеживания CVE;
  закрытие путей к админ-панелям (`/admin`, `/wp-admin` и т.п.), отсутствие дефолтных учёток.
- **Секреты в CI/CD и репозиториях:** сканирование на утечки токенов/ключей, ротация, отдельные
  окружения; отсутствие продакшн-секретов в git-истории.

## 6. Организационные меры

- **security.txt** (`/.well-known/security.txt`) с контактом для ответственного раскрытия уязвимостей.
- **Регулярный внешний пентест** (не реже раза в год и после крупных релизов) + при желании bug bounty.
- Обучение разработчиков безопасной разработке (SSDLC), ревью безопасности в процессе релизов.
- Периодический аудит соответствия PCI DSS и 152-ФЗ.
- Управление подрядчиками/агентствами: требования к безопасности доступа в B2B-портал.

## 8. Топ-10, с чего начать прямо сейчас

1. Убедиться, что карты не обрабатываются на своей стороне; включить SRI+CSP и убрать сторонние
   скрипты со страниц оплаты; подтвердить 3-D Secure.
2. Проверить сегментацию: имеет ли веб-фронт прямой доступ к продакшн-БД/CRM (не должен).
3. Прогнать проверку на IDOR в личном кабинете и бронированиях.
4. Закрыть `.git/`, `.env`, бэкапы, source maps, открытые swagger/debug на проде.
5. Включить MFA для админов и кабинетов турагентов.
6. Настроить/проверить security-заголовки (HSTS, CSP, nosniff, frame-ancestors) и TLS-конфиг.
7. Инвентаризировать поддомены; закрыть dev/staging и dangling-записи.
8. Настроить SPF/DKIM/DMARC.
9. Добавить rate limiting на логин, восстановление пароля, формы и API.
10. Опубликовать security.txt и запланировать внешний пентест.

## 9. Чек-лист безопасных пассивных проверок «живого» сайта

Эти проверки неинвазивны (не атакуют приложение) и подходят для продакшена. Выполнить их
не удалось из-за блокировки сети — прогоните вручную или из окружения с доступом.

**Заголовки и TLS**
- `curl -sSI https://fstravel.com/` — заголовки; наличие HSTS, CSP, nosniff, X-Frame-Options; отсутствие `Server`/`X-Powered-By` с версиями.
- SSL Labs (ssllabs.com/ssltest) — оценка TLS-конфига, протоколов, шифров, цепочки.
- securityheaders.com — быстрая оценка security-заголовков.

**Раскрытие информации**
- Проверить коды ответа: `/.git/HEAD`, `/.env`, `/server-status`, `/phpinfo.php`, `/.well-known/security.txt`, `/sitemap.xml`, `/robots.txt`.
- Поиск `*.map` (source maps) в подключаемых JS; поиск ключей/токенов в клиентском JS.
- Просмотр HTML `<head>`: generator/meta-теги, версии CMS/фреймворков, комментарии.

**Инфраструктура и домен**
- Перечисление поддоменов (crt.sh по домену, публичные CT-логи) → поиск dev/stage/dangling.
- Проверка SPF/DKIM/DMARC (DNS TXT-записи, mxtoolbox).
- Fingerprint технологий (Wappalyzer/BuiltWith) → сверка версий с известными CVE.

**Поверхность приложения**
- Инвентаризация форм и их `action`-URL; параметры в URL поиска туров.
- Инвентаризация XHR/fetch-эндпоинтов из вкладки Network браузера → карта API.
- Проверка наличия открытых swagger/openapi/GraphQL introspection.

> Активные проверки (SQLi, IDOR, брутфорс, fuzzing, полноценный пентест) выполнять **только**
> с письменного согласования, на согласованных стендах и во временном окне — не по этому чек-листу.
