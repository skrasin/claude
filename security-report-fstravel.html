Исходящий доступ к fstravel.com заблокирован сетевой политикой окружения (403 на CONNECT); обход политики не применялся. Поэтому документ — это модель угроз, приоритизированные рекомендации и чек-лист безопасных пассивных проверок, а не находки по фактической текущей конфигурации. 01

Витрина почти никогда не бывает статичной

Формально это сайт с информацией. На практике на том же домене и поддоменах у туроператора живут поиск и подбор туров, онлайн-бронирование и оплата, личный кабинет клиента, B2B-портал для 670+ агентств и десятки форм — и именно эти динамические функции, а не статический контент, образуют поверхность атаки.

Первый шаг — инвентаризация всей поверхности: домены, поддомены, эндпоинты, формы, API, интеграции. Защитить можно только то, что учтено. Ключевой архитектурный принцип: публичный сайт не должен иметь прямого сетевого доступа к внутренним системам и продакшн-БД — между ними сегментация (DMZ), API-gateway с авторизацией и сервисные учётки с минимальными правами.

04

Рекомендации по направлениям

P0

Платёжные данные и защита от веб-скиммеров

  • Не обрабатывать карты у себя. Hosted payment page или изолированный iframe / редирект на страницу эквайера (PCI SAQ A).
  • Обязательный 3-D Secure 2.0 на всех платёжных операциях.
  • На страницах оплаты — строгий CSP и ноль сторонних скриптов (аналитика, чаты, теги недопустимы на checkout).
  • Subresource Integrity (SRI) для всех внешних <script> и <link>; мониторинг целостности JS.
  • Подтвердить фактический уровень соответствия PCI DSS.
P0

Разделение витрины и внутренних систем

  • Сетевая сегментация: веб-фронт в DMZ, нет прямого пути к продакшн-БД, CRM, ERP.
  • Доступ к внутренним данным — только через API-gateway с аутентификацией и авторизацией.
  • Сервисные учётки по принципу наименьших привилегий; секреты в secret manager, не в коде на диске.
P0

Инъекции и валидация ввода

  • Только параметризованные запросы / ORM; запрет конкатенации ввода в SQL, команды, шаблоны.
  • Валидация по «белым спискам» и контекстное экранирование вывода (против XSS).
  • WAF в режиме блокировки как компенсирующий контроль — не замена исправлениям.
P0

Авторизация и IDOR / BOLA

  • Серверная проверка прав для каждого объекта (заказ, клиент, документ), а не по UI.
  • Непредсказуемые идентификаторы (UUID) вместо последовательных числовых ID.
  • Тест: может ли пользователь A открыть данные пользователя B, поменяв ID в запросе.
P0

Раскрытие секретов и артефактов на проде

  • Закрыть /.git/, /.env, бэкапы .bak/.old/.zip, /debug, /phpinfo, открытые source maps и swagger без авторизации.
  • Убрать из клиентского JS секретные ключи API — в браузер попадают только публичные ключи с ограничениями.
P1

Аутентификация и сессии

  • MFA обязателен для админов, сотрудников и кабинетов турагентов — B2B-портал приоритетная цель.
  • Cookies: Secure, HttpOnly, SameSite; ротация сессии при логине.
  • Rate limiting против брутфорса и credential stuffing; единообразные ответы (против user enumeration).
  • Безопасное восстановление пароля: одноразовые токены с TTL, без утечки в реферере и логах.
P1

Защита клиентских данных · 152-ФЗ

  • Минимизация: не собирать и не отдавать лишнее; маскирование в интерфейсах.
  • Шифрование ПДн в покое и в транзите; ограничение экспорта и выгрузок.
  • Разграничение доступа сотрудников + журналирование обращений к данным.
  • Соответствие 152-ФЗ: согласия, локализация ПДн граждан РФ, политика конфиденциальности.
P1

API-безопасность · OWASP API Top 10

  • Инвентаризация эндпоинтов; закрытие теневых и устаревших версий API.
  • Авторизация на уровне объектов и функций; защита от mass assignment.
  • Отключить GraphQL introspection в проде; ввести rate limiting и квоты.
P1

Транспорт и HTTP-заголовки безопасности

  • Только TLS 1.2/1.3, современные шифры, корректная цепочка; редирект HTTP→HTTPS.
  • HSTS, CSP (nonce / strict-dynamic), X-Content-Type-Options, frame-ancestors, Referrer-Policy, Permissions-Policy.
  • Убрать раскрытие версий в Server и X-Powered-By.
P1

Поддомены, DNS и почта

  • Инвентаризация поддоменов; поиск dangling-записей (риск subdomain takeover).
  • Закрыть публичные dev/staging/test-стенды — частый источник утечек и мягкая точка входа.
  • Настроить и проверить SPF, DKIM, DMARC (DMARC в quarantine/reject) против фишинга под брендом.
P2

Дополнительные меры

  • Supply chain: аудит всех тегов, аналитики, чат-виджетов; минимизация, SRI, регулярный пересмотр.
  • Загрузка файлов: валидация типа и размера, антивирус, хранение вне webroot, без выполнения.
  • SSRF: белые списки хостов, запрет доступа к внутренним адресам и облачным метаданным.
  • Rate limiting / антибот на формах, поиске туров и API против скрейпинга и DoS.
  • Мониторинг: централизованные логи безопасности, алерты, контроль целостности файлов, план реагирования.
  • Патч-менеджмент: актуальные версии CMS и библиотек, отслеживание CVE, отсутствие дефолтных учёток.
ORG

Организационные меры

  • /.well-known/security.txt с контактом для ответственного раскрытия уязвимостей.
  • Регулярный внешний пентест (минимум раз в год и после крупных релизов), при желании bug bounty.
  • Безопасная разработка (SSDLC), ревью безопасности в релизном процессе.
  • Периодические аудиты соответствия PCI DSS и 152-ФЗ; требования к безопасности доступа для агентств.
05

С чего начать прямо сейчас

  1. Убедиться, что карты не обрабатываются на своей стороне; SRI + CSP и ноль сторонних скриптов на оплате; подтвердить 3-D Secure.
  2. Проверить сегментацию: имеет ли веб-фронт прямой доступ к продакшн-БД или CRM.
  3. Прогнать проверку на IDOR в личном кабинете и бронированиях.
  4. Закрыть .git, .env, бэкапы, source maps, открытые swagger и debug.
  5. Включить MFA для админов и кабинетов турагентов.
  6. Настроить security-заголовки (HSTS, CSP, nosniff, frame-ancestors) и TLS-конфиг.
  7. Инвентаризировать поддомены; закрыть dev/staging и dangling-записи.
  8. Настроить SPF / DKIM / DMARC.
  9. Добавить rate limiting на логин, восстановление пароля, формы и API.
  10. Опубликовать security.txt и запланировать внешний пентест.
06

Чек-лист безопасных пассивных проверок

Неинвазивны и подходят для продакшена. Их не удалось выполнить из-за блокировки сети — прогоните вручную или из окружения с доступом.

Заголовки и TLS

  • curl -sSI https://fstravel.com/ — наличие HSTS, CSP, nosniff, X-Frame-Options; отсутствие версий в Server
  • SSL Labs — оценка протоколов, шифров, цепочки
  • securityheaders.com — быстрая оценка заголовков

Раскрытие информации

  • Коды ответа: /.git/HEAD, /.env, /server-status, /.well-known/security.txt, /robots.txt
  • Поиск *.map и ключей/токенов в клиентском JS
  • HTML <head>: generator, версии CMS, комментарии

Инфраструктура и домен

  • Перечисление поддоменов через crt.sh и CT-логи → dev/stage/dangling
  • Проверка SPF / DKIM / DMARC (mxtoolbox)
  • Fingerprint технологий (Wappalyzer) → сверка с известными CVE

Поверхность приложения

  • Инвентаризация форм и их action-URL; параметры поиска туров
  • Карта API: XHR/fetch из вкладки Network браузера
  • Открытые swagger / openapi / GraphQL introspection

Важно: активные проверки — SQLi, IDOR, брутфорс, fuzzing, полноценный пентест — выполнять только по письменному согласованию, на согласованных стендах и во временном окне. Не по этому чек-листу.
